5. **Task [Extended] - Restore approach debugging** (v0.6.16): Multi-iteration debugging of save/restore lifecycle, discovered WidgetTracker overwrites workspace data<br>
   **Result**: Investigated why terminals restored at notebook root despite saved cwds. Source-dived JupyterLab core bundle to trace `terminal:create-new` command handler - reads `args.cwd` and passes to `startNew({name, cwd})`. Attempted workspace data injection approach: patching `terminal:N` stateDB entries with `{data: {name, cwd}}` during save phase. Playwright MCP testing revealed entries were correctly written but restore still failed. Root cause: `RestorablePool.save()` calls `this._restore.args(widget)` which for terminals returns only `{name}` - overwrites our injected cwd on every widget track event. Also discovered `persistCwds` creating ghost `terminal:N` entries for terminals not in layout, polluting Running Terminals sidebar. Final approach: pre-create terminals via `app.started.then()` which fires after all plugins activate but before `ILayoutRestorer` replays commands. Built-in `terminal:create-new` finds pre-existing sessions via `connectTo()` instead of creating new ones at root. Added `getLayoutTerminalNames()` to read layout dock widgets and clean stale cwds. Fixed README metapackage name `stellars_jupyterlab_extensions` to `stellars_jupyterlab_fixes`. Debug logging tagged `[restore-terminals-fix]` retained for ongoing testing. This approach was later superseded once testing proved the WidgetTracker overwrite makes any client-side workspace injection unwinnable.

6. **Task [Extended] - Relative cwd restore fix** (v0.6.18): Root-caused silent restore-at-root and fixed via server-computed relative cwd<br>
   **Result**: Every prior restore approach failed for one reason: we stored the absolute cwd. JupyterLab's built-in restore runs the stored cwd through `contents.localPath()`, which strips the leading slash, the server then double-prefixes it with the server root, the resulting path does not exist, and the terminal silently falls back to root. The frontend cannot fix this alone - `PageConfig serverRoot` is reported as `~/workspace` (tilde, unresolvable client-side), so the conversion must happen server-side. Added `_to_relative_cwd()` in `routes.py` using `os.path.relpath` against `server_root_dir`, returning `None` for the root itself or paths outside it; both `/cwd/{name}` and `/cwds` handlers now emit a `relative_cwd` field. Rewrote `src/index.ts` to a pure save-side plugin: `patchTerminalCwd()` writes the relative path into the existing `terminal:<name>` workspace entry only (patch-only - no ghost entries, per-workspace isolated via IStateDB, closed-tab terminals never force-reopened). Capture happens on `widgetAdded` (2/4/8s retries for pty spawn lag) plus a 15s poll for `cd` between opens. Restore is then the stock terminal plugin reading our patched entry - no `cd`, no race, no pre-creation, no blocking `activate`. Removed all dead approaches (pre-creation, `app.started`, ghost-entry creation, `getLayoutTerminalNames`, debug logging). Validated the full save->restart->restore loop on an isolated throwaway server (port 9911, own config dir): seeded terminal restored into `subdir_alpha/deep`, a live `cd` to `subdir_beta` was captured by the 15s poll into the workspace entry, and after a real server restart the terminal reopened in `subdir_beta` - zero console errors throughout. Save phase uses widgetAdded retries at 2s/4s/8s plus 15s bulk poll, both layout-filtered.

7. **Task [Extended] - Server-side pre-creation restore** (v0.9.25): Final working fix - moved restore entirely server-side after the relative-cwd approach still failed live<br>
   **Result**: Entry 6's `relative_cwd` patching looked right but failed on the real server. Inspecting the actual workspace file revealed why: JupyterLab's `RestorablePool.save()` rewrites each `terminal:<name>` entry with name-only data (its `args(widget)` callback returns just `{name}`) the instant the widget is tracked during restore - the live poll re-adds cwd afterward, so the file shows a cwd now, but at the moment restore reads it the cwd is already gone. No client-side injection can win that race. Pivoted fully server-side. `routes.py` now persists terminal cwds to a per-server-root JSON state file under `jupyter_data_dir/restore_terminals_fix/state-<sha1>.json` (hash of the realpath'd root, so distinct roots never clobber each other). Added a `POST /state` handler that receives the in-layout terminal names from the frontend and snapshots each running terminal's cwd via the existing `/proc` process-tree walk, replacing prior state so closed tabs drop off. `prepopulate_terminals()` reads that file on startup and re-creates each saved terminal through `terminal_manager.create(name, cwd)`. Wired into `__init__.py` via `IOLoop.current().call_later(1.0, ...)` - deferred so the terminals server extension has installed `terminal_manager` into `web_app.settings` first (server-extension load order is unguaranteed), and crucially it runs before any browser connects, so the stock restore's `terminal:create-new {name}` finds the session already running and `connectTo`s it in its saved cwd instead of starting a fresh shell at root. `src/index.ts` collapsed to a thin reporter: on `widgetAdded` (2s/5s retries for pty spawn lag) and a 15s poll it POSTs the tracker's terminal names to `/state`. Dropped `IStateDB` dependency, `relative_cwd` workspace patching, and all client restore logic. Workspace switching A->B->A already worked because the server stays alive and sessions persist (built-in `connectTo` handles it); only a server restart kills sessions and lost cwd, which this fixes. Validated the full restart->restore loop on an isolated throwaway server (server log confirmed `pre-created terminal 1 at .../alpha/deep` before any browser, terminal then reopened there with zero console errors), then confirmed working live on the real server.
